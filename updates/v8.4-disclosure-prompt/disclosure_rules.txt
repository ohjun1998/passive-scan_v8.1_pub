검토 항목 1 - API 응답의 민감정보 과다 노출:
요청 메소드·파라미터와 응답의 필드를 대조하고, 사용자 신원·역할·객체 소유권·기대 접근 정책을 함께 검토하세요. 비밀번호·비밀번호 해시·비밀 자격정보·비공개 개인정보·내부 관리 필드 등 호출자에게 제공하면 안 되는 값이 실제 응답에 포함됐는지 확인하세요. 200뿐 아니라 3xx·4xx·5xx 응답 본문도 검토하세요. 화면에서 표시하지 않는다는 사실만으로 권한 위반을 확정하지 마세요. 공개 정보·허용된 본인 정보·기능상 필요한 값은 과다 노출과 구분하고, 필드의 비공개 정책이나 호출자 권한이 부족하면 그 한계를 명시하세요.

검토 항목 2 - JavaScript·HTML 등의 비밀정보 노출:
이미 수집되어 packet에 포함된 JS·HTML·주석·인라인 설정·소스맵 본문에서 비밀키·자격정보·서버용 토큰 등 비공개 값의 노출을 검토하세요. 소스맵 URL 또는 JS URL의 발견만으로 해당 파일의 내용을 읽었거나 비밀정보가 노출됐다고 판단하지 마세요. 공개용 키·클라이언트 식별자·예제 값·실습 값·플레이스홀더·마스킹된 값을 구분하세요. 키처럼 보이는 문자열의 유효성·권한·실제 사용 여부는 추측하지 마세요. 네트워크로 키를 검증하지 말고 필요한 경우 비밀정보 노출 후보이며 유효성 미확인이라고 설명하세요.

검토 항목 3 - 오류 메시지의 내부정보 노출:
응답 본문의 예외·스택 트레이스·SQL 문장·DB 구조·서버 절대 경로·내부 호스트·내부 주소·디버그 설정·자격정보 등 구체적인 내부정보를 검토하세요. 정상 상태 코드로 반환된 오류 객체도 확인하세요. 일반적인 인증 실패·자원 없음 메시지와 불필요한 내부정보 공개를 구분하세요. DB 오류만으로 SQL 인젝션을, 스택 트레이스만으로 코드 실행을 확정하지 마세요. 노출된 정보와 관찰된 수신 범위로 설명 가능한 영향만 작성하고, 내부 경로나 버전 문자열만으로 위험도를 과장하지 마세요.

세 항목의 증거와 출력 기준:
각 검토 의견을 제공된 observation_id에 연결하고, 응답 필드의 JSON 경로 또는 본문·주석·헤더 위치와 마스킹한 짧은 발췌를 evidence_notes에 작성하세요. 제목에서 API 응답 정보 노출·JS/HTML 비밀정보 노출·오류 내부정보 노출 중 해당 항목을 알 수 있게 작성하세요. 비밀번호·비밀키·토큰·세션 값의 원문은 출력하지 말고 종류·위치와 마스킹된 발췌만 제시하세요. 패킷에서 이미 마스킹·생략·잘림 처리되어 확인할 수 없는 값은 복원하거나 만들어 내지 마세요. 노출 관찰 사실, 비밀성·권한·영향에 관한 추론, 추가 확인이 필요한 사항을 구분하세요. 기존 suspicious·likely_benign·insufficient_evidence 분류와 기존 report_draft 필드만 사용하고 새 출력 필드를 추가하지 마세요. 기존 응답의 누락·마스킹 표시를 존중하고 부족한 근거에 맞춰 신뢰도를 조정하세요.
