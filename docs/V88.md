# v8.8.0 — PortSwigger 주제 기반 후보 추천 확대

2026-10-15에 확인한 [Web Security Academy 공식 목록](https://portswigger.net/web-security/all-topics)의 취약점 관련 30개 주제를 33개 추천 유형에 연결했습니다. Essential skills는 취약점 종류가 아닌 진단 방법이므로 유형 수에서 제외했습니다. 기존 IDOR·인가를 별도 유형으로 유지하고 정보 노출을 민감정보·비밀값·상세 오류로 나눴으므로 주제 수와 유형 수가 다릅니다.

기준은 후보 추천입니다. [Burp Scanner 개별 이슈 목록](https://portswigger.net/burp/documentation/scanner/vulnerabilities-list)의 모든 검사나 자동 검증을 구현했다고 표시하지 않습니다. 아래 상태·단서는 이 프로젝트의 저장 자료용 규칙이며 PortSwigger가 탐지 정확도를 보증한 규칙이 아닙니다.

## 세 가지 표시

| 표시 | 의미 | 기본 AI 처리 |
|---|---|---|
| 단서 후보 | 구체적인 오류·상충 정책·입력/응답 관계 등 저장 단서가 있음 | 기존 예산 안에서 우선순위·유형별 선택 |
| 기능 점검 대상 | API·업로드·OAuth 등 기능을 발견했지만 결함 근거는 부족함 | 선택에서 제외 |
| 추가 수집 필요·미평가 | 현재 자료 형식으로 필요한 정보를 판단할 수 없음 | 취약점 의견을 만들지 않음 |

HTML은 단서 후보를 기본 표시하며 구분 필터에서 기능 점검 대상을 볼 수 있습니다. `recommendations.json`의 `candidates`는 두 종류의 항목 전체이고, `summary.signal_candidates`와 `review_surfaces`가 각각의 수입니다. 기록 한 개에 여러 항목이 생길 수 있으므로 항목 수는 취약점 수가 아닙니다.

`type_coverage`는 모든 33개 유형의 상태·공식 출처·추가 확인 사항을 제공합니다. `no_matching_saved_signal`은 지원 규칙의 일치 단서가 없다는 뜻이며 안전 판정·완전한 검사 완료가 아닙니다. 실제 근거 위치 검증과 취약점의 의미 검증도 구분합니다.

## 실행

```bash
# 기존 명령 그대로, 모델 호출·대상 요청 없음
python ai_review.py recommend --report reports/requests \
  --scope example.test --output reports/candidates-v88

# 기본: 우선 단서 후보 최대 24개만, 8개씩·동시 2개
python ai_review.py recommend --report reports/requests \
  --scope example.test --output reports/candidates-v88-ai --ai

# 선택: 기능 점검 대상까지 기존 AI 상한 안에 포함
python ai_review.py recommend --report reports/requests \
  --scope example.test --output reports/candidates-v88-surfaces \
  --ai --ai-include-surfaces --ai-limit 24

# 전체 범주의 합성 예제: 모델·대상 접속 없음
python examples/v88/demo.py --output reports/v88-demo
```

`--authority`, `--ai-batch-size`, `--ai-workers`, 실행 제한·모델 선택·종료 코드·새 출력 폴더 규칙은 [v8.7 사용법](V87.md)을 유지합니다. 기본 AI는 기능 점검 대상 때문에 호출 수를 늘리지 않습니다. 유형 수가 선택 상한보다 크면 전 유형이 AI 검토되지 않으며 미선택 항목을 보존합니다. `--ai-include-surfaces`도 상한을 늘리지 않습니다.

## 단서의 해석과 정상 대조

- SSRF는 URL 입력만 있으면 기능 점검 대상이며 같은 호스트의 접속 오류가 함께 있을 때 단서 후보를 만듭니다. DNS 조회·접속·콜백 검증은 수행하지 않습니다.
- XXE는 XML 사용과 파서 오류를 구분하고 DTD·외부 엔티티의 명시적 차단 오류를 성공 단서로 쓰지 않습니다. 엔티티를 확장하거나 XML의 외부 자료를 읽지 않습니다.
- 경로 탐색은 경로 선택 입력만 있으면 기능 점검 대상이며 상위 경로 표기와 파일 형태의 응답이 함께 있어도 실제 파일 경계 위반은 별도 판단합니다.
- 명령어·SSTI·NoSQL·역직렬화는 구체적인 처리기 오류를 단서로 사용합니다. 오류 문자열이 문서·예제·일반 실패일 수 있으며 실행·주입을 확정하지 않습니다. 직렬화된 객체를 실제로 복원·실행하지 않습니다.
- CORS는 credentialed null/교차 Origin 관계를 찾지만 정상 신뢰 Origin일 수 있습니다. 공개 wildcard와 credential 조합을 브라우저의 성공한 비공개 읽기 근거로 사용하지 않습니다.
- CSRF는 쿠키·상태 변경 가능성·단순 요청·표식 부재를 기능 점검 대상으로 제시합니다. 토큰 부재만으로 취약점이라 하지 않으며 Origin/Referer·SameSite 등 다른 방어를 확인해야 합니다.
- 클릭재킹은 상호작용 HTML과 저장된 프레임 정책을 함께 봅니다. 유효한 X-Frame-Options 또는 제한적 frame-ancestors가 있으면 이 규칙의 단서를 만들지 않습니다. Report-Only나 default-src만으로 프레임 차단을 가정하지 않습니다.
- Host 반영, 캐시 HIT·Age, 개인 관련 동적 응답과 정적 확장자 등 관계를 단서로 쓰되 캐시 키·교차 사용자 재사용은 확인하지 않습니다.
- 정상 API·GraphQL/introspection·LLM·JWT/JWKS·OAuth·업로드·DOM 패턴·반복 업무 요청은 그 자체로 결함이 아닙니다. 업무 음수 입력도 환불·할인일 수 있으며 2xx는 최종 상태 반영을 보증하지 않습니다.

## 저장 형식의 한계

정규화가 제거한 Content-Length·Transfer-Encoding, 원시 바이트·프로토콜/연결 정보로 요청 스머글링을 판정하지 않습니다. 해당 유형은 항상 추가 수집 필요·미평가로 표시합니다. 경쟁 상태는 별도 동시 실행·최종 상태 근거가 필요하고, WebSocket은 HTTP 업그레이드 외의 메시지 프레임이 없을 수 있습니다. multipart는 파일 바이트를 생략합니다.

JWT·쿠키·자격정보는 기존 마스킹을 유지합니다. 토큰의 alg·서명·클레임이나 쿠키 속성을 마스킹 값에서 추측하지 않습니다. 공개 JWKS·라이브러리 단서를 기능 점검 대상으로만 다룹니다.

기존 마스킹이 `Access-Control-Allow-Credentials`의 프로토콜 boolean까지 지우던 문제를 고쳤습니다. 이 정확한 헤더의 소문자 `true/false`만 보존하고 그 외 자격정보는 계속 마스킹합니다. [Fetch 표준](https://fetch.spec.whatwg.org/#http-new-header-syntax)에 맞춰 대문자 `TRUE`를 유효한 `true`로 바꾸지 않습니다. 이미 마스킹된 과거 값은 복원하지 않으며 CORS 범위에 자료 부족을 표시합니다. 새 규칙이 과거에 생략된 본문을 복구하지도 않습니다.

[검증 기록](V88_VERIFICATION.json)에는 합성 표본·실제 모델 실행·기존 77기록 회귀를 구분합니다. 합성 예제 성공은 운영 서비스의 탐지 정확도나 취약점 재현을 뜻하지 않습니다. 기존 인가 라벨 50개를 다른 유형의 정답으로 사용하지 않습니다. 대상 추가 요청·자동 공격·키 인증·취약점 확정은 이번 범위 밖입니다.
