# 2026-10-15 — 대상 추가 요청 없는 저장 증거 분석 고도화

## 사용자 요청과 적용 범위

> 보안 엔지니어들이 passive scan + LLM 조합을 어떻게 활용하는지 알 수 있을까? 그리고 활용 부분을 현재 개발하고 있는 시스템에 도움이 될만한 요소는?

> 요청이 없는 패시브 스캔 기반의 발전 방향인거지?

> 상기 발전 방향으로 프로젝트 고도화 해줘

사용자의 기존 “일단은 후보를 추천하는 단계만 진행해보자”와 병합·진행 승인을 유지했다. 새 요청이 없다는 조건은 **진단 대상 추가 요청·DNS 없음**으로 적용했다. 이미 저장한 자료를 분석하며, 선택적 ChatGPT 로그인 모델 서버 통신은 발생한다. 기존 URL 수집·크롤링·httpx와 분석 경로를 구분한다.

## 구현과 판단

- 관련 계정 대조·같은 기능의 입력 변형·응답 차이·저장 값 흐름을 후보에 연결했다. 객체 ID·입력 값을 지워 같은 자원으로 합치지 않는다. 실제 신원과 인과관계가 확인됐다고 쓰지 않는다.
- 전체 저장 증거와 관련 의존성, 범위, 실제 프롬프트, 요청 모델, CLI·인증/설정의 지문을 캐시 키에 연결했다. 캐시는 완료·도구 비활성화·JSON 의미·원본 패킷·프롬프트 해시를 다시 확인한 과거 결과만 재사용한다. 로컬 무결성 확인을 외부 서명 증명으로 표현하지 않는다.
- 규칙 단서가 없는 저장 자료의 제한된 묶음을 LLM에 전달하는 `--discover`를 추가했다. 각 의심 대상은 자료 내 ID와 URL 외 실제 근거가 있어야 한다. 최대 3개, medium/low 가설이며 취약점 확정·재현으로 표시하지 않는다.
- 새 AI 검토 예산은 기본 24단위를 공유한다. 기본 탐색은 4묶음까지, 규칙 후보는 최대 8개씩, 동시 2개다. 캐시 적중은 새 예산을 사용하지 않아 다음 미검토 자료로 진행한다.
- 사람의 후속 점검 채택·기각·맥락 보류를 별도 이력에 추가하고 후보 ID와 전체 증거 해시 일치 시만 반영했다. 사람 메모는 모델 명령에 넣지 않는다. 기각 후보도 증거와 함께 보존한다.
- HTML에서 관련 기록의 마스킹 표시 사본·응답 차이·근거 위치·과거 재사용·사람 판정을 볼 수 있게 했다. 표시 제한과 저장 자료 완전성을 구분한다.
- 버전 8.9.0, CI 데모, README·사용법·유스케이스·남은 단계·릴리스 문서를 갱신했다. 기존 명령·과거 평가·PortSwigger 30주제/33유형·httpx 20워커와 각 `-rl 10 -t 5`는 유지한다.

## 실제 검증에서 발견한 문제와 수정

처음에는 정상 가격 기록과 의심 가격 기록을 각각 탐색 대상으로 전달해, 정상 비교 기록에도 같은 의심 가설이 붙었다. 묶음을 중복 제거하고 모델이 그 안의 실제 의심 대상 ID를 선택하도록 변경했다. 각 선택 대상에 자신의 URL 외 근거가 필요하며, 비교 자료·명시적 허용 대조군을 인가 위반 대상으로 바꾸는 결과를 거부한다. 이 수정은 과거 v8.6 평가의 오탐 2건을 소급해서 지우지 않는다.

캐시 첫 실제 재실행에서는 유효한 결과가 있어도 모델 호출이 반복됐다. 프로세스마다 프록시 인증정보와 루프백 리스너 포트가 바뀌어 설정 지문이 달라지는 것이 원인이었다. 모델 설정이 아닌 이 임시 전송 핸들만 지문에서 정규화했다. 원격 프록시 경로·TLS 관련 환경·Codex 인증/설정 파일·요청 모델·프롬프트·전체 증거 변경은 계속 반영한다. 실제 전송·인증·실행 전 검사 자체는 바꾸지 않았다. 초기 실패 실행을 최종 재사용 성공으로 집계하지 않는다.

최종 후보 프롬프트에는 관련 증거의 관계가 인과·같은 자원·정상성을 증명하지 않으며 각 후보를 독립 검토한다는 지침도 명시했다. 실제 재검증 한 묶음에서 모델 첫 응답 제한시간이 발생했다. 완료된 4단위는 캐시에 보존하고 실패 묶음을 명시적 재실행으로 복구했다. 지연·실패를 완료나 안전으로 집계하지 않는다.
