# 2026-10-15 — 여러 취약점 유형의 후보 추천

## 사용자 요청과 범위

사용자는 처음 목표가 매핑된 요청·응답에서 IDOR·인가, XSS, SQLi, 민감정보, API KEY·TOKEN의 취약점 가능성이 높은 부분을 제시하는 것이라고 설명했다. 전체 비교 묶음의 장시간 AI 검토와 인가 중심 접근에 대한 논의 후 다음과 같이 요청했다.

> 일단은 후보를 추천하는 단계만 진행해보자

저장 자료에서 후보·근거·다음 확인을 추천하는 단계만 구현했다. 자동 재현·키 인증·최종 취약점 확정은 범위에 넣지 않았다. 이전의 “병합하고 진행해도 되는데 AI 문제 좀 해결해줘” 승인은 유지되며, 코드·문서·검증 결과를 먼저 준비하고 GitHub CI 후 반영한다.

## 변경

- `ai_review.py recommend`와 유형별 규칙·짧은 모델 판단·HTML/JSON 출력 경로를 추가했다. 기본값은 모델 호출 0회다.
- 범위 내 저장 본문 전체에서 지원 단서를 선별한다. 선택 AI 검토는 기본 최대 24개 후보, 최대 8개씩, 동시 2개이며 압축 패킷당 24KiB 이하로 제한한다.
- 유형별 첫 선택 슬롯을 배정해 인가 후보가 다른 유형을 모두 밀어내지 않게 했다. 선택 상한이 유형 수보다 작으면 전 유형이 포함되지는 않는다.
- 모델은 후보 ID별 채택·기각·추가 맥락, 우선순위·짧은 이유·다음 확인만 반환한다. 긴 보고서 초안을 생성하지 않는다. 기존 읽기 전용 Codex 전송·완료 검사를 공통 함수로 재사용한다.
- 판단 대상과 정상 비교 자료를 `subject_ids`와 `support_ids`로 분리했다. 근거 위치와 마스킹 발췌를 로컬 증거에 대조하고 모델이 해당 관계를 바꾸지 못하게 했다.
- 미선택·실패·크기 초과 후보를 숨기지 않는다. 일부 모델 실패 시 종료 코드 3과 결과를 함께 제공한다. 원본·과거 배치 결과를 덮어쓰지 않는다.
- 정상 요청 인증 헤더·쿠키를 노출로 분류하지 않고 일반 OAuth 발급 필드, 이스케이프·일반 텍스트·JSON 반영을 대조했다. 기존 소스의 비밀값도 재마스킹한다.
- VERSION과 패키지 버전을 8.7.0으로 일치시켰다. 수집 httpx 20워커와 각 `-rl 10 -t 5`는 유지했다.

## 검증

- 새 기능 테스트 21개 통과. 전체 294개 중 290개 통과, 실제 Chromium·고정 httpx/Katana를 사용하는 선택 테스트 4개는 별도 CI 대상이다.
- 혼합 합성 표본 12기록에서 6개 유형 후보 6개가 나왔다. 정상 소유자·이스케이프 HTML·일반 HTML 텍스트·JSON 반영·OAuth 발급·health 대조군은 판단 대상이 아니다.
- 기존 ChatGPT 로그인 Codex CLI 0.162.1로 혼합 후보 6개를 호출 1회에 실제 검토했다. 약 31.551초, 완료·후보 ID·스키마 검증 통과. AI 결과는 후속 검토 추천 1개·추가 맥락 5개이며 취약점 확정 0개다.
- 기존 77기록은 규칙 처리 약 0.077초, 후보 29개(인가 6·IDOR 7·민감정보 13·비밀값 3)였다. 우선 24개를 실제 모델 호출 3회·기본 동시 2개로 약 67.270초에 검토했다. 실패 0, AI 미검토 후보 5개를 유지했다.
- 기존 인가 라벨 50개와 규칙의 판단 대상만 대조하면 의심 13개는 선택, 정상 37개는 미선택이다. 이는 모델 판정 정확도나 XSS·SQLi·비밀값 정확도가 아니다. 과거 v8.6.1의 오탐 2건을 삭제하거나 재평가 결과로 대체하지 않았다.
- 과거 36묶음 전체 보고서 검토와 이번 24후보 검토는 작업량이 다르므로 같은 커버리지의 속도 향상으로 주장하지 않는다. 대상 추가 요청·키 인증·자동 재현은 모두 0건이다.

## 후속 판단

운영 자료에서 후보의 실질적인 후속 가치는 서비스 정책과 신원·입력 맥락을 아는 진단자가 검토해야 한다. 규칙 비탐지는 안전 판정이 아니며, 새 추천 경로의 교차 실행 캐시·자동 재시도는 이번 범위에 추가하지 않았다.
