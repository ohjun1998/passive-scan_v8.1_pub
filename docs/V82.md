# v8.2 증거 중심 진단 지원

[신규·개선·유지 기능을 강조한 유스케이스 다이어그램](USE_CASES.md)

저장소 이름은 `passive-scan_v8.1_pub`을 유지하며 내부 버전은 8.2.0입니다. 원본 v8 저장소는 수정하지 않습니다. httpx의 20개 워커와 각 `-rl 10 -t 5`도 유지합니다. 외부 AI 호출은 추가하지 않았습니다.

## 추가한 기능

| 기능 | 동작 | 대상 추가 요청 |
|---|---|---|
| 계정·조직·기능 라벨 | actor, tenant, scenario, capture_id, expected_access, operation 저장 | 없음 |
| 증거 기반 우선순위 | 요청 필드·실제 관찰·응답 필드·기능 맥락·기대 권한으로 이유와 다음 확인 사항 제시 | 없음 |
| 계정 비교 | 같은 URL·메소드·완전한 payload·표현 관련 헤더의 서로 다른 계정 관찰 비교 | 없음 |
| 기능 흐름 | 같은 capture/기능/계정/조직 내 응답 ID·URL과 다음 요청 값의 연결 추정 | 없음 |
| 커버리지 | 발견·실제 요청 확보·검토 예정·검증 중·확인·오탐·보류 구분 | 없음 |
| JS 변경 분석 | 내용 SHA-256와 분석기 바이너리 해시 기준 캐시·추출 결과 재사용·추가/제거 구조 요약 | 기본 캐시 적중 시 없음 |
| OpenAPI/HTML form import | 메소드·필드·선언 타입·필수 필드 추출. body 예시값 생성·외부 ref 조회·폼 제출 없음 | 없음 |
| 선택적 검증 큐 | 명시적으로 선택한 관찰의 조회 baseline 수집 | 있음, 별도 예산 |
| GraphQL AST 검사 | 선택 operation·fragment 확장·순환·깊이·필드/alias·페이지 크기 검사 | 허용된 조회에만 있음 |

점수는 검토 순서이며 취약점 확률이 아닙니다. 필드명, 2xx, 응답 차이 또는 차이 없음만으로 취약점/정상을 자동 판정하지 않습니다. 자동으로 `confirmed`나 `false_positive` 상태를 기록하지 않습니다.

## 설치와 예제

```bash
python -m pip install -r requirements-v81.txt
python request_inventory.py import examples/v82-demo.jsonl --scope example.test
python request_inventory.py report --xlsx
```

`reports/requests/index.html`의 요청/후보, 계정 비교, 커버리지, 기능 흐름, JS 변경분을 확인하세요. 대상 접속 없이 예제 파일만 처리합니다. 검색 결과는 100개씩 표시합니다.

실제 트래픽을 계정별로 가져오는 예:

```bash
python request_inventory.py import imports/user-a.har --scope example.com --actor user-a --tenant org-a --scenario "주문 조회" --capture-id order-a-1 --expected-access allow --operation read
python request_inventory.py import imports/user-b.har --scope example.com --actor user-b --tenant org-a --scenario "같은 주문 조회" --capture-id order-b-1 --expected-access deny --operation read
python request_inventory.py report --scope example.com --xlsx
```

라벨에는 계정 별칭을 사용하며 실제 토큰을 입력하지 마세요. 라벨은 사용자가 제공한 맥락이며 로그인 상태를 자동 인증하지 않습니다. 서로 다른 계정의 토큰이 동일한 마스킹 값이 되어도 observation ID가 달라집니다. 비어 있는 라벨은 기존 v8.1 observation ID를 유지합니다.

수동 브라우저 기록에도 같은 라벨을 사용할 수 있습니다.

```bash
python -m pip install -r requirements-browser.txt
python -m playwright install chromium
python record_browser.py --url https://example.com --scope example.com --actor user-a --tenant org-a --scenario "파일 업로드부터 다운로드" --operation unknown --seconds 300
```

기록기는 capture_id를 자동 생성하며 직접 지정할 수도 있습니다. 자동 클릭·자동 폼 제출은 없습니다. scope는 저장 범위이며 사용자 행동의 전송을 차단하는 규칙은 아닙니다.

## 비교와 흐름의 정확성

- 다른 자원 ID와 다른 payload는 같은 요청으로 비교하지 않습니다. JSON 속성 순서는 정규화하되 값과 배열 순서는 유지합니다.
- 요청 body가 불완전한 관찰은 자동 비교에서 제외합니다. multipart 파일 바이트가 생략된 경우도 동일 payload라고 가정하지 않습니다.
- 응답이 누락되거나 생략된 경우 본문 비교 불가로 표시합니다. HTTP 상태 차이는 별도로 남깁니다.
- 기본적으로 응답 body 필드를 모두 비교합니다. 변동 필드는 `--ignore-response-field '$.meta.requestId'`처럼 정확한 JSON 경로로 지정할 수 있으며 원래 증거는 변경하지 않습니다.
- JSON 배열 후반 값·빈 객체/배열·타입과 폼 중복 필드도 비교합니다. 비교 복잡도 12,000개 노드/깊이 32를 넘으면 본문 비교 불가로 표시하며 동일하다고 판정하지 않습니다.
- 마스킹 때문에 서로 다른 비밀값이 동일하게 보일 수 있습니다. 기대 권한과 실제 반환 자원을 함께 검토해야 합니다.
- 표시용 숫자/UUID 경로 묶기는 증거 ID나 URL을 병합하지 않습니다. 같은 경로여도 메소드·필드 구조가 다르면 별도 커버리지 항목입니다.
- 비교 화면은 그룹당 최대 30개 관찰, 전체 최대 1,000쌍입니다. 표시 제한 수를 알리고 모든 원본 관찰을 요청 화면과 JSONL에 유지합니다.
- 흐름은 같은 capture_id/scenario/actor/tenant로 묶으며 타임스탬프로 정렬합니다. 앞선 응답과 뒤 요청의 값 일치는 추정이며 서버 의존 관계를 증명하지 않습니다. 시각이 부정확한 수집 파일은 흐름 순서도 검토해야 합니다.

## 검토 상태 저장

HTML에서 상태·메모를 변경한 뒤 `검토 변경 내보내기`를 누르면 `review_edits.json`이 생성됩니다. 이 동작은 현재 화면의 상태만 바꾸므로 DB 반영에는 가져오기가 필요합니다.

```bash
python request_inventory.py review --file imports/review_edits.json
python request_inventory.py report --xlsx
```

명령으로 한 항목을 기록할 수도 있습니다.

```bash
python request_inventory.py review --id OBSERVATION_ID --state deferred --note "실제 응답 body 확보 필요"
```

`confirmed`와 `false_positive` 결론에는 증거 메모가 필요합니다. 기존 관찰에만 적용할 수 있으며 잘못된 ID가 섞인 일괄 수정은 롤백합니다. 보고서에서 표기한 미검토/미수집은 정상 판정이 아닙니다.

## OpenAPI와 폼 가져오기

```bash
python request_inventory.py import imports/openapi.yaml --scope example.com --base-url https://example.com/api
python request_inventory.py import imports/page.html --format html --scope example.com --base-url https://example.com/page
```

OpenAPI 3.x/Swagger 2.0 JSON/YAML과 저장된 HTML form을 지원합니다. `--base-url`은 API 기준 URL을 명시적으로 덮어씁니다. 문서의 경로 template은 실제 ID로 채우지 않으며 정적 발견으로 표시합니다. 로컬 JSON pointer ref만 제한된 깊이로 해석하고 외부 ref는 가져오지 않습니다. 필드·타입을 담은 `schema` 메타데이터는 JSONL/증거 파일/전체 기록에서 확인할 수 있습니다. 명세/폼에 적힌 기본값·비밀값은 요청 body로 복사하지 않습니다.

## JS 분석과 변경분

다운로드 메타데이터에 내용 해시와 분석 결과를 함께 보존하고 이전 실행의 `recon_history.db`에서 복원합니다. 다운로드 이력만 있는 구버전 캐시는 새 분석기 정보가 필요할 때 보호 예산 안에서 다시 다운로드합니다.

- 같은 내용 해시·분석기 버전이면 저장된 정적 추출 결과를 재사용합니다. 캐시 전부 적중 시 재다운로드하지 않습니다.
- 분석기 바이너리 해시 또는 adapter 버전이 바뀌면 기존 캐시 분석을 그대로 사용하지 않습니다.
- 추가/제거 endpoint는 메소드·URL·body 필드 구조 기준입니다. JS 런타임의 실제 값이나 실행 여부를 증명하지 않습니다.
- 분석 캐시는 자산당 최대 500개 구조를 저장합니다. 최초 현재 분석에서는 전체 추출 결과를 출력하고 DB에 보존합니다. 이후 캐시 재사용에서 나머지 구조의 이전 관찰은 역사 자료로 남습니다. 이전 캐시가 부분적이면 변경 요약의 `delta_partial`을 표시합니다.
- 변경 목록 미리보기는 각 10개이며 전체 추가/제거 개수도 제공합니다. body 값 변화나 서버 기능 변화 전체를 뜻하지 않습니다.
- 기본 7일 다운로드 캐시는 현재 서버 내용의 재확인이 아닙니다. 로컬 `download_js.py --revalidate`는 ETag/Last-Modified가 있고 재사용 가능한 분석이 있을 때 조건부 요청을 한 번 수행합니다. 304도 네트워크 요청이며 예산에 포함됩니다. 자동 재시도는 없습니다.

## 선택한 요청의 조회 baseline

보고서의 `review_queue.json` 또는 아래 명령으로 큐를 생성합니다.

```bash
python review_queue.py build --scope-file scope.txt
```

각 항목에 evidence ID·우선순위·추천 이유·baseline 실행 가능 여부가 표시됩니다. 실행은 선택한 ID에만 적용합니다.

```bash
python review_queue.py execute --active --scope-file scope.txt --queue reports/requests/review_queue.json --id OBSERVATION_ID --actor user-b --tenant org-a --expected-access deny --headers-file imports/runtime_headers.json
```

`runtime_headers.json`은 사용자가 준비한 JSON header 객체입니다. 필요하지 않으면 생략합니다. 해당 파일에는 세션 정보가 들어갈 수 있으므로 `imports/`에 보관하고 Git에 올리지 마세요. 큐에는 자격 증명을 넣지 않고, 전송에만 사용하며 새 증거에는 마스킹합니다.

- 모든 선택의 ID·URL·메소드·전송 정책을 DB와 대조한 후 첫 요청을 보냅니다. 큐의 URL을 바꿔 임의 목적지로 보내는 동작은 차단합니다.
- 실제 관찰된 GET/HEAD 또는 제한된 GraphQL query POST만 기본 실행 대상입니다. UNKNOWN·정적 추출·마스킹된 body/URL은 실행하지 않습니다.
- 일반 조회 POST는 관찰에 `operation=read` 라벨이 있고 실행 시 정확한 `--read-post-url`을 지정한 경우에만 허용합니다. GraphQL mutation/subscription은 이 옵션으로 우회하지 않습니다.
- 업로드·삭제·결제·메일 발송·자동 payload 변경·메소드 변경·자동 취약점 확인은 수행하지 않습니다. 수동 기록/import 기능은 그대로 사용할 수 있습니다.
- 검증 큐는 별도 상태 DB에서 기본 20회(최대 설정 100회), 최소 1초 간격, 총 10 MiB, 응답당 1 MiB를 적용합니다. 기존 httpx 속도·워커 설정을 바꾸지 않습니다.
- redirect를 자동 추적하지 않으며 429/503·반복 오류·지속 지연은 중단합니다. 고비용 경로 예산 소진은 해당 항목을 보류하고 다른 조회를 계속할 수 있습니다.
- 결과를 `validation_baseline` 출처와 명시적인 actor 라벨로 저장하고 원본 관찰 ID에 연결합니다. 원본은 검증 중으로 표시하며 성공 응답을 취약점 확정으로 바꾸지 않습니다.

GET이나 GraphQL query, `operation=read` 라벨은 서버 내부 부작용을 증명하지 않습니다. 조회용 POST의 의미와 기대 권한은 사용자가 확인해야 합니다. 현재 큐는 baseline 관찰과 비교를 돕는 기능이며 독립적인 취약점 자동 검증 엔진은 아닙니다.

## GraphQL AST 제한

graphql-core로 구문을 파싱하고 operationName이 선택한 query를 검사합니다. 다중 operation은 명시적 선택이 필요하며 선택되지 않은 mutation을 실행하지 않습니다. fragment를 확장해 순환을 차단하고 최대 1,000 tokens, 깊이 10, fields 100, aliases 30, 페이지 크기 100, payload 8 KiB를 적용합니다. 자동 introspection과 subscription은 허용하지 않습니다. 구문 분석 실패 때 정규식 허용으로 우회하지 않습니다. 그래도 query의 서버 resolver 비용·부작용을 보장할 수는 없습니다.

## 출력과 호환성

`requests.jsonl`/`evidence/`에 context·schema·asset·triage·review 정보가 추가됩니다. `analysis.json`에 커버리지·비교·흐름을 저장하고 `review_queue.json`에 실행 전 검토 목록을 저장합니다. Excel에는 Candidates/Coverage/Compare/Flows v8.2 시트를 추가합니다. 기존 Requests/Structures v8.1 시트명은 호환성을 위해 유지합니다.

이전 인벤토리 DB와 JS 캐시 테이블은 읽을 때 새 테이블/열을 추가하며 관찰 내용을 삭제하지 않습니다. 보고서 생성은 대상에 접속하지 않습니다. 자동 정찰은 계속 수동 workflow_dispatch에서만 시작하고, push CI는 가상/루프백 검증만 수행합니다.
